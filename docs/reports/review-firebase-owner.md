# Firebase and owner integration review

Decision: request changes before pilot approval. Reviewed the supplied diff, integration plan, reports and current source; accepted the reported emulator, build and real OpenShorts playback evidence. No live services called or tests rerun.

1. **[P1] Replacement and Wi-Fi re-scan discard saved framing.** `firebase-api/src/app.ts:580` only loads the currently paired device, while the authorized replacement flow has already cleared `shop.device_id` and saved `replacement_context.previous_device_id`. Moreover, lines 597–598 always initialize the new reference path/revision to null, including ordinary re-scan. `owner-app/src/screens/Qr.tsx:52` then sends rescan users directly to Camera, bypassing reference capture. This contradicts the promised framing carryover and leaves the new pairing without its drift reference. Fix: transactionally resolve the prior device from current pairing or replacement context, verify its shop ownership, carry its reference path/revision into the new device, and clear consumed replacement context. Cover unpair → pair and ordinary rescan, including retrieval of the inherited reference through the new device capability.

2. **[P1] File sharing loses the required browser gesture on slow downloads.** `owner-app/src/lib/share.ts:26–31` waits for the complete MP4 download before invoking `navigator.share`. When download time outlasts transient activation, native sharing rejects; the later URL share and popup fallback also lack activation, so the owner can tap Share and get no usable result. The [Web Share specification](https://www.w3.org/TR/web-share/) explicitly requires transient activation. Fix: prepare/cache the file before enabling the final Share action, or prepare after the first tap and request a second explicit tap to invoke native sharing synchronously. Refresh expired capabilities during preparation, surface failures, and preserve successful-share-only event recording. Add a test proving the final share action performs no preceding network await; verify on a physical mobile browser when available.

3. **[P2] Selecting an older day does not load it until the next poll.** `owner-app/src/screens/Home.tsx:36` replaced the date-dependent effect with `usePolling`; `owner-app/src/hooks/usePolling.ts:33` only restarts for interval/enabled changes. Tapping an older date or Back updates state but makes no request for up to 30 seconds, leaving the prior clips visible (Back immediately relabels them Today). Fix: trigger an immediate request on date changes alongside polling, and ignore responses from superseded dates. Verify older-date and Back actions immediately request and display the intended date.

No additional important owner-isolation, scoped raw-upload, transactional lease/completion, deletion-revocation or daily-SMS acknowledgement defect was established in this bounded review. Hosted configuration and physical-device behavior remain separate validation limits.
