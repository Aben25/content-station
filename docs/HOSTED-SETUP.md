# Hosted Firebase / Google Cloud setup

The local integration is independently runnable. This document separates the remaining hosted configuration from verified local behavior. No commands here were executed against production during implementation.

1. Select the Firebase project. The old Content Station project is `lemekeru` (display name `sutway`), with a Standard Firestore database. A shared project must preserve its existing resources and access rules. Never deploy the repository's deny-all rules over the old app's rules without merging/scoping them appropriately. A separate named database and dedicated v2 bucket provide a clearer boundary; set `FIRESTORE_DATABASE_ID` when using a named database.
2. Deploy the API container using `firebase-api/Dockerfile` with repository root as build context. Configure its runtime service account with only the needed Firestore and dedicated-bucket access. Admin SDK uses application default credentials in Cloud Run; no private key file belongs in the image or client apps. Configure `GCLOUD_PROJECT`, `FIREBASE_STORAGE_BUCKET`, public HTTPS `API_BASE_URL`, and exact `OWNER_ORIGIN`. Do not set any emulator-host environment variables on hosted services.
3. Put independently generated `DEVICE_JWT_SECRET`, `MEDIA_SECRET`, `ENGINE_API_KEY` and `CRON_SECRET` values in Secret Manager and mount them into the API. Give the worker only its engine key and optional explicitly selected model credentials. It uploads/downloads through scoped API capabilities and does not require database credentials.
4. Enable Firebase phone Authentication and configure authorized owner domains. Retrieve the web app's public Firebase config, then build the owner app with `VITE_FIREBASE_API_KEY`, `VITE_FIREBASE_AUTH_DOMAIN`, `VITE_FIREBASE_PROJECT_ID` and the HTTPS `VITE_API_BASE_URL`. Remove the local `.env.local` when preparing a hosted build, or override all its values explicitly. `VITE_FIREBASE_AUTH_EMULATOR_URL` must be empty and `VITE_DEMO_MODE` must be false. Host the built website on Firebase Hosting or another HTTPS static host.
5. Run the `engine-worker/Dockerfile` image as an always-running worker, initially one instance. A [Cloud Run worker pool](https://docs.cloud.google.com/run/docs/overview/what-is-cloud-run) supports this model. A default request-driven service can stop allocating CPU while idle. Image building and hosted runtime behavior still need validation in the chosen project.
6. Schedule an authenticated POST to `/internal/cron/tick` every minute using `x-cron-secret`. This drives retention, stale device detection, recovery and daily delivery. Store scheduler credentials appropriately. Enable live SMS only after actual sender configuration; `SMS_MODE=dry-run` never marks a notification delivered. Phone sign-in SMS and daily clip SMS have separate provider setup.
7. Build the wall iPhone app with the hosted HTTPS API URL. Verify pairing, camera permissions, real capture, thermal fallback, network loss/recovery, app restart and re-pairing on hardware. Upload a new TestFlight build only after those checks and release configuration are ready.
8. Run an isolated hosted pilot with two test owners and one phone. Verify one owner's tokens cannot access another shop, restart a worker mid-job, confirm a clip reaches the owner website and revoke its media on deletion. The local tests do not replace this hosted/hardware pass.

Firebase's [Auth emulator documentation](https://firebase.google.com/docs/emulator-suite/connect_auth) explains the local-only test tokens and phone flow used during verification. Do not enable emulator handling on production services.

The separate Supabase implementation is not a required deployment component. Current API route shapes and Firebase changes are documented in `firebase-api/README.md` and `docs/INTEGRATION-PLAN.md`.
